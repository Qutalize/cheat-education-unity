# レッスン05 まとめ：なぜサーバー権威が解か

---

## 1. ここまでの対応表

| チート | なぜ効くか（共通の型） | クライアント側で足せる防御 | 構造的な解 |
|---|---|---|---|
| ESP / ウォールハック | 全プレイヤー座標がクライアントに同期される | 不審コンポーネント走査・描画フック検出（回避可能） | サーバーが**見えない敵を送らない**（`CheckObjectVisibility` ＋ 視線 `NetworkShow/Hide`） |
| エイムボット / ホーミング | 狙い・弾道・命中判定がクライアント | 命中率の統計監視（事後・強さを絞ると無力） | サーバーが**命中を再検証**（ラグ補償つき） |
| 武器数値強化 | ダメージ・弾数の計算がクライアント | 数値の難読化（延命策） | サーバーが**数値の正本を持ち計算する**（SO ＋ ServerRpc ＋ `NetworkVariable`(server)） |
| スピード / テレポート / 無敵 | 位置・体力がクライアント権威 | 整合性チェック（回避可能） | `NetworkTransform` を **Server Authority** に＋移動量検証＋体力 `NetworkVariable`(server) |

**共通の型**: どのチートも「クライアントが情報を持っている / 計算している」から成立する。
違うのは、その情報が座標なのか数値なのか、という点だけ。

## 2. 4象限で体感する

各チートについて、以下の 4 通りを実際に切り替えて観察する。

| | 対策なし | 対策あり（該当レッスンの実装） |
|---|---|---|
| **チートなし** | 素のゲーム。正常 | 正常（体感差はほぼ無い or 少しラグ） |
| **チートあり** | チートが成立する（ESP で透けて見える等） | チートが**無効化**される（ESP の枠が物陰で消える等） |

手順:
1. Multiplayer Play Mode で Host + Client を起動。
2. Client 側で F1 パネルからチートを 1 つ ON。
3. 対策スクリプトを付けていない状態で「成立」を確認。
4. 対策スクリプト（`Countermeasures/`）を付けて再テスト。「無効化」を確認。
5. チートを OFF にして、対策ありでも正常に遊べることを確認（＝正規プレイヤーへの副作用チェック）。

## 3. クライアント側防御はなぜ「時間稼ぎ」なのか

| 防御 | 何をする | なぜ破られるか |
|---|---|---|
| メモリ難読化（`ObscuredFloat` / CodeStage Anti-Cheat Toolkit 等） | 値を暗号化して保存、読むとき復号 | 復号処理もクライアント内にある。全走査するツールは復号後の値を必ず見つける |
| 整合性チェック（ハッシュ・CRC 監視） | 改ざんを検知してログ／切断 | 検知コードも攻撃者と同じプロセス。検知の直前に値を戻す等で回避 |
| カーネルモード アンチチート（EAC / BattlEye） | ドライバでプロセス・メモリを監視 | 更に下（ハイパーバイザ・別 PC からの DMA・VM introspection）から攻撃される |
| 描画ステートの門番（本体プロジェクトの J-03 相当） | 敵ドローの深度 ALWAYS を拒絶 | エンジンより上位（RenderDoc・API フック）からの改変には無力。ESP・数値チートには無反応 |

**実測データ**（Collins & Chothia et al., MATE Workshop 2024）:
11 タイトルのクライアント側アンチチートと 80 のチート販売サイトを調査し、
**「強力なカーネル型アンチチートはチートを根絶せず、価格を上げ稼働時間を下げるだけ」**と結論。
チート市場は年 $12.8M〜73.2M、月 3〜17 万人が購入。
＝クライアント側防御の役割は「攻撃コストを上げる」ことであって「無くす」ことではない。

## 4. サーバー権威が「構造的な解」である理由

> **送っていない情報は、どんな手段でも改変できない。**
> **サーバーが計算した結果は、クライアントを何をしても変わらない。**

これは描画方式・実装言語・OS・アンチチートの有無に**一切依存しない**。
クライアントがどれだけ改造されても、「壁の向こうの敵の座標」がそのクライアントに
届いていなければ、ESP は描くものが無い。ダメージをサーバーが計算していれば、
`damage = 9999` は表示が変わるだけ。

### 実在する手本
| 実装 | やっていること |
|---|---|
| **ioquake3**（GPLv2・ソース公開） | サーバーが PVS でエンティティ送信を絞る（`sv_snapshot.c`）＋ anti-cheat 版は視線判定を追加（`sv_wallhack.c`） |
| **BlackMirror**（ACM CCS 2020） | 信頼実行環境（Intel SGX）内で可視性テスト → 見えるエンティティだけ選択的開示（精度 97%） |
| **米国特許 US 11,771,997 B2**（TooMuchVoltage Software） | サーバー GPU がレイトレで pair-wise 可視性行列を作り、送信パケットを各プレイヤーごとにフィルタ |
| **Netcode for GameObjects** | `NetworkObject.CheckObjectVisibility` / `NetworkShow` / `NetworkHide` / Server Authority `NetworkTransform` / `NetworkVariable` の Write 権限 |

この教材で `Countermeasures/` に実装したものは、**上の業界標準解法を Unity の API で
なぞったもの**。思いつきの防御ではなく、実在の手本の縮小再現。

## 5. サーバー権威の「限界・コスト」も正直に

- **レイテンシ**: 入力→サーバー→結果 の往復ぶん、操作に遅延が乗る。予測＋補正で
  隠すが、完全には消えない（peeker's advantage 等）。
- **サーバー負荷・費用**: 全員ぶんのシミュレーション・可視性判定・ヒット検証を
  サーバーが行う。プレイヤー数 × tick rate に比例。ホスティング費用が要る
  （P2P / リステンサーバーなら「ホスト」が有利＝別の公平性問題）。
- **実装の網羅性**: 一箇所でもクライアント計算・クライアント権威が残ると、そこが穴。
- **完全には検知できないもの**: エイムボットを人間の限界内に調整されると、
  サーバー検証・統計監視の両方をすり抜ける（レッスン02）。

→ だから現実のゲームは「サーバー権威（土台）＋クライアント側アンチチート（コスト増）＋
統計/ML 検知（洗い出し）」を**多層で**組む。だが**土台がサーバー権威でなければ、
上に何を積んでも砂上の楼閣**、というのがこの教材の結論。

## 7. この教材の締め

チート対策を **「クライアントを賢くする」問題**として解こうとすると、
攻撃者は常にクライアントの中にいるので勝てない。
**「サーバーが何を送り、何を信じるか」の問題**に置き換えたとき初めて、
描画方式にも言語にも OS にも依存しない、構造的な守りができる。

Unity（Netcode for GameObjects）は、そのための道具を最初から持っている。
足りないのは道具ではなく、**既定のまま出荷せず、正しく使うこと**。
